# 분석 품질 출시 점검표

실행일: __________ / 검토자: __________ / 커밋: __________

## 실행 순서

1. `npm run prices:sync`로 가격 스냅샷과 기준일을 갱신한다. 변경된 가격은 검토 후 커밋한다.
2. `npm run catalog:check-links`로 카탈로그 출처의 최종 응답과 허용 호스트를 확인한다.
3. `.env.local`에 `ANTHROPIC_API_KEY`와 `CLAUDE_MODEL`을 설정하고 `npm run evals`를 실행한다. 실제 모델 호출에는 비용이 든다. 기존 셸 환경 변수가 있으면 그 값을 우선한다.
4. `evals/results/<실행 시각>/report.md`와 시나리오별 `<id>.json`을 읽고 아래 세 기준을 순서대로 확인한다. 실행 시각은 UTC이며 결과 폴더는 git에서 제외된다. 결과 폴더는 모델을 호출하기 전에 만들고, 같은 밀리초에 시작한 실행이 있으면 `<실행 시각>-2`처럼 번호를 붙이므로 여러 실행을 동시에 시작해도 결과가 겹치지 않는다.

하나만 재실행: `npm run evals -- --scenario reservation-web-app`

키 없이 도구 점검: `npm run evals -- --dry-run` (두 옵션을 함께 쓸 수도 있다).
모의 실행은 모든 시나리오에 같은 샘플 출력을 적용한다. 예상되는 자동 점검 실패를 실제 품질 실패로 해석하지 않는다. 끝까지 실행하면 종료 코드 0이며, 실제 실행은 자동 점검 실패가 하나라도 있으면 코드 1이다. 인자·설정·파일 저장 오류는 두 모드 모두 실패다.

`npm run evals`는 `tsx --conditions=react-server`로 서버 전용 서비스 래퍼를 실행한다. `server-only` import를 제거하지 않는다. 시나리오는 순차 실행하며 결과 JSON에는 입력·기대값, 검증된 전체 분석 결과 또는 실패 단계·오류, 자동 점검 결과와 사용량이 들어 있다.

보고서의 모델 비용은 Claude API가 반환한 토큰 수에 Anthropic 공개 단가(`src/lib/llm/claude-cost.ts`)를 곱한 USD이며, 실패한 분석의 사용량도 집계한다. 단가표에 없는 모델·대체 모델 응답·누락 비용은 0으로 추정하지 않고 총 비용·평균을 미확정으로 표시한다. 실제 실행의 건당 평균 원가를 확인한 뒤 PRD의 무료·Pro 한도 조정 근거로 쓴다. 모의 실행의 비용 0은 실측 원가가 아니다.

## 1. 요구사항에 맞는 서비스가 선택되었는가

- `scenarios.json`의 입력과 `expect.notes`를 보고서 및 전체 결과 JSON과 대조한다.
- 세 안의 서비스·수량·연결·장점, 추천 이유, 사용량 가정을 확인한다. 자동 점검은 분류 존재 여부만 확인하므로 PostgreSQL·Redis 선택, 복제본 수량, 불필요한 DB와 같은 적합성은 직접 확인한다.
- 자동 점검 '예산 표현 일치'는 안별 제목·장점에서 '예산을 넘·초과', '예산 안·내·이내', '예산에 맞' 같은 표현이 계산 비용(예산 이하/초과)과 반대인지 키워드로만 본다. 부정('넘지 않', '안에 들지 않')은 뜻을 뒤집어 판정한다. 가능성·조건·의도('넘을 수 있', '넘으면', '맞추려고'), 다른 안을 함께 말하는 문장, 여러 안을 다루는 추천 이유 문단은 판정하지 않으므로 이런 문장의 예산 설명은 직접 확인한다.
- 높은 가용성 요구가 실제 중복 구성에 반영되는지 본다. 범위 밖은 LLM 챗봇 1건이며, 지원하지 않는 기능과 비용 범위를 설명하는지 확인한다. 단순 사내 관리 웹앱은 웹앱·DB 범위로 평가한다.
- 예산 기대값은 `calculatePlanCost`로 참조 아키텍처의 `low` 단계 비용을 계산해 정한다. 현재 스냅샷에서 가장 싼 기본 구성은 `serverless-static-web-app`이다. 정적 포트폴리오는 해당 단계의 정적 호스팅 항목만 적용하고, Redis 요구에는 기본 최저 비용에 Managed Redis B0 1노드 비용을 더한다. 5만 원 MVP는 기본 최저 비용이 예산을 넘으므로 예산 이내를 필수로 요구하지 않는다. 가격 갱신으로 이 관계가 바뀌면 기대값과 근거를 함께 검토한다.

## 2. 예상 비용이 Azure 공식 가격 계산기 대비 허용 오차 안인가

허용 오차: **미정** (PRD 미확정 사항). 임의의 합격 기준이나 계산기 금액을 채워 넣지 않는다.

각 시나리오에서 다음 절차를 반복한다.

1. 추천 안의 JSON에서 구성요소 ID·수량, 항목별 비용·가정, 가격 기준일을 확인한다.
2. Azure 공식 가격 계산기를 열고 지역 **Canada Central**, 통화 **CAD**로 맞춘다. `priceRegion`이 있는 구성요소는 해당 지역(Static Web Apps: `eastus2`, Front Door: `Zone 1`)으로 확인하고 메모에 남긴다.
3. `src/catalog/components.json`의 서비스·SKU·과금 단위와 동일하게 선택한다. 상시 리소스는 월 730시간, 사용량 항목은 결과에 표시된 요청 수·전송량·저장량을 입력한다. 무료 구간, HA 노드와 저장소 중복 수량도 일치시킨다.
4. 계산기 월 합계와 CloudSight 추천 안 합계의 차액을 기록한다. 오차율은 `|CloudSight 합계 - 계산기 합계| / 계산기 합계 × 100`으로 기록한다. 계산기 합계가 0이면 오차율은 해당 없음으로 두고 차액만 기록한다.
5. 계산 일시와 계산기 설정·내보내기 자료를 별도로 보관한다. 기준일 차이, 누락 항목, 단위 차이를 조사한다. 허용 오차가 정해지기 전에는 수치만 기록하고 비용 합격 판정은 보류한다.

## 3. 출처 링크가 모두 유효한가
